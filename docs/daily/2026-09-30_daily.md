# Tagesbericht Entwicklung — 2026-09-30

## Zusammenfassung

Die API kann jetzt den Typ eines Items ändern. Weil das ID-Präfix der Typ ist, bekommt das Item dabei die nächste freie ID des neuen Typs, und alle Verweise im Backlog ziehen mit. Die Antwort nennt zusätzlich die alte ID und einen Hinweis, dass Verweise außerhalb des Backlogs (Techdocs, Tagesberichte, Code, Commits) nicht angepasst wurden. Im Detail-Panel gibt es dafür den Button „🔁 Typ ändern“: Nach dem Wechsel ist das Item unter der neuen ID ausgewählt, und ein Hinweis nennt alte und neue ID sowie die möglichen Verweise außerhalb des Backlogs. Veröffentlicht sind `v0.1.1` (Endpunkt), `v0.2.0` (geändertes Antwortformat) und `v0.2.1` (UI), aber noch nicht im laufenden Container: dafür fehlt `./todo.sh update`. Zwei Backend-Tests, die vom echten Datum abhingen, laufen jetzt mit festem Datum und sind grün. `TASK-002`, `STORY-007` und `EPIC-001` sind bestätigt und abgeschlossen; `STORY-018` wartet auf Bestätigung. Außerdem sind die Architekturregeln so geöffnet, dass ein Projekt künftig wahlweise in Markdown-Dateien oder in einer zentralen Datenbank gespeichert werden darf; im Code sind dafür das Feld `Source.backend`, ein Routing je Projekt und eine gemeinsame Test-Suite für die Speicher-Ports vorbereitet (noch kein zweites Backend). Die Farbe der Priorität „Normal“ ist Grau statt Violett. Veröffentlicht ist `v0.2.2`. Danach wurde der Dokumentzugriff umgebaut: Notizen und Specs werden intern nur noch über Item-ID und Dokumentnamen angesprochen, die Ordnerstruktur `items/<ID>/` kennt allein der Markdown-Adapter. Nach außen ändert sich dabei nichts außer einmalig der `version` von Items mit Dokumenten; ein Release gab es dafür nicht. Zuletzt kam die zentrale Datenbank dazu: Ein Projekt, das in `config.json` mit `"backend": "database"` eingetragen ist, wird vollständig in SQLite (`configs/todo.db`) gespeichert, samt Archiv, Papierkorb, Notizen und Specs, und funktioniert über dieselbe API. Markdown-Projekte bleiben unverändert, die Datenbankdatei entsteht erst bei Bedarf. Veröffentlicht als `v0.3.0`; im laufenden Container erst nach `./todo.sh update`. Mit `v0.4.0` liegt auch die Projektliste samt UI-Zustand in dieser Datenbank: Datenbank-Projekte lassen sich über `POST /api/v2/sources` anlegen, und eine bestehende Installation übernimmt beim ersten Zugriff ihre Projekte aus `config.json` und `ui_state.json` (Sicherungen `.bak`). Dabei bekommen alle Projekte neue `source_id`s (UUID). Der laufende Container hat noch den alten Stand; die Übernahme passiert erst mit `./todo.sh update`. Mit `v0.5.0` lässt sich ein Datenbank-Projekt auf Anforderung mit einem Markdown-Ordner abgleichen (`POST /api/v2/sources/{id}/sync`, beide Richtungen): erst eine Vorschau, dann Ausführen mit dem Token der Vorschau; was auf dem Ziel fehlt, bleibt stehen und wird nur mit `delete_missing` gelöscht. In der Oberfläche gibt es das noch nicht (STORY-024). `STORY-022` und `STORY-023` sind bestätigt. Mit `v0.5.1` lässt sich das Backend eines Projekts an Ort und Stelle umstellen (`PUT /sources/{id}` mit neuem `backend`), aber erst nach einem Sync: Sind die Seiten verschieden, kommt 409 `sync_required` und nichts ändert sich. Dafür liest der Sync auch ein Markdown-Projekt in die Datenbank (`from_md`). Die `source_id` und die Item-IDs bleiben gleich, der Ordner wechselt zwischen `path` und `sync_path`. `TASK-003` ist bestätigt. Mit `v0.6.0` ist das alles in der Oberfläche bedienbar: Beim Hinzufügen wählt man Markdown-Ordner oder Datenbank, Datenbank-Projekte tragen das Kürzel „DB“, ein Sync-Dialog zeigt erst eine Vorschau (mit Warnliste für Fehlendes auf dem Ziel) und führt dann aus, und „In die Datenbank übernehmen…“ bzw. „Als Markdown-Ordner ablegen…“ stellt ein Projekt mit gleichen Item-IDs um. `STORY-024` ist bestätigt. Für `STORY-025` wurden die Techdocs zum Betrieb ergänzt und dieses Backlog probeweise in die Datenbank übernommen und wieder zurückgeschrieben (auf einer Kopie, in eigener Scratch-Konfiguration): gleiche Item-Versionen und Dokumente, Export → Import → Export byteidentisch. Ein neues Release gab es dafür nicht (nur Dokumentation); `STORY-025` wartet auf Bestätigung, danach entscheidet der Projekteigner, welches Backend dieses Projekt dauerhaft nutzt. Zuletzt wurde die Architekturregel 1 für das nächste Epic (EPIC-004) geöffnet: Ein Projekt hat künftig eine primäre Quelle und darf die andere Seite als Spiegel halten; im Code ändert sich dabei noch nichts.

## Entscheidungen und Alternativen

| Entscheidung | Grund und Alternativen | Nachweis |
|---|---|---|
| Typwechsel als eigener Endpunkt mit neuer ID statt als `PATCH`-Feld | Die Adresse des Items ändert sich, das passt nicht zu einer Feldänderung. Die ID zu behalten hätte den Typ und das Präfix auseinanderlaufen lassen. | 8674de9 |
| Hinweis auf Verweise außerhalb des Backlogs als `notices` in der Antwort | Der Server kann Techdocs, Berichte und Code nicht anpassen. Ein Code mit englischem Text lässt die UI übersetzen und Agenten auf Anfrage nach der alten ID suchen. Eine eigene Abfrage oder ein Header wurden verworfen, weil die Antwort selbst den Hinweis trägt. | siehe Merge „Typwechsel: Antwort mit alter ID“ |
| Dokumente über Item-ID und Namen statt Pfade, Umbau vor dem Datenbank-Adapter | Der Port war pfadbasiert, weil es nur Markdown gab; eine DB hätte sonst Ordner und Pfade nachbauen müssen. Fremde Pfade (außerhalb `items/<ID>/`) bleiben als Name erhalten; in den konfigurierten Backlogs kommen sie nicht vor (alle 105 Verweise geprüft). | 909e4c8 |
| Sync mit Token statt gespeicherter Vorschau; neue Ports statt Logik im Adapter | Ein Token aus den Versionen beider Seiten hält den Server zustandslos; ändert sich eine Seite, muss die Vorschau neu geholt werden. Die Ports konnten kein ganzes Backlog schreiben, daher `write_backlog`; das Löschen einzelner Dokumente braucht `delete_document`. Verworfen: Sync-Logik im Adapter (widerspricht der Architekturregel) und ein Löschen aller Items der Zielseite (verlöre Dokumente und `uid`s). | 4f4aafd, [STORY-023](../todo/items/STORY-023/STORY-023_notes.md) |
| Spiegel auf beiden Seiten erlaubt, Sync bleibt ausdrücklich und nie automatisch | Das Arbeiten auf der Datenbank mit Markdown als Spiegel soll möglich sein. Ein automatisches Nachziehen nach jedem Schreiben wurde zurückgestellt (Fehlerfälle bei nicht beschreibbarem Ordner, Regeländerung nötig); stattdessen Badge bei abweichendem Spiegel. | 8998119, STORY-028 |
| Speicher-Backend je Projekt wählbar (Markdown oder zentrale Datenbank), DB intern mit UUID und Label | Die Datenbank soll mit UUIDs arbeiten, API und Markdown weiter mit Schlüsseln wie `STORY-019`; ein Typwechsel ändert dann in der DB nur das Label. Verworfen: Datenbank nur als Cache neben Markdown (widerspricht „keine eigene Kopie“) und automatische Spiegelung (Konflikte ohne saubere Lösung); stattdessen Sync nur auf Anforderung mit Vorschau. | f64b4cc |
