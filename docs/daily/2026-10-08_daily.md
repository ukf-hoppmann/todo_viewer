# Tagesbericht 2026-10-08

## Zusammenfassung

Grundlage für EPIC-005 (Notizen und Wiedervorlage) gelegt: Die Architekturregeln beschreiben jetzt Topics, Notes, Links und Auslöser, und die zentrale Datenbank hat dafür Modell, Migration und Speicher-Adapter. Für Nutzer ist noch nichts sichtbar, es gibt weder API noch Oberfläche für Notes. `STORY-037` und `STORY-038` warten auf Bestätigung.

Am selben Tag folgte die Logik darauf: Auslöser, Fälligkeit, Wiedervorlage, Archiv und Papierkorb für Notes sind als Domain-Regeln und `NoteService` umgesetzt und getestet. `STORY-040` und `STORY-043` warten auf Bestätigung.

Danach kam die HTTP-API dazu (`STORY-039`, Release v0.7.0): Topics, Notes, Links, Auslöser, Dokumente einer Note, ein schlanker Index ohne Langtexte, ein Zähler für fällige Notes, eine Fällig-Liste über alle Projekte und die zwei Optionen sind jetzt über `/api/v2` erreichbar. Dabei fiel ein Fehler auf: Links von Notes folgten einem Item beim Typwechsel nicht, weil der Retype die Source-ID statt des Projektnamens übergab. Das ist behoben. Eine Oberfläche gibt es weiter nicht. `STORY-039` und die Tasks `TASK-004` bis `TASK-009` warten auf Bestätigung.

Zuletzt kamen die Änderungshinweise (`STORY-041`, Release v0.7.1): Wird ein verlinktes Item abgeschlossen, verworfen, gelöscht oder im Typ geändert, bekommt die Note einen Hinweis und ist fällig, bis jemand entscheidet (behalten, abkoppeln, verwerfen). Wird eine Note verworfen oder befördert, bekommen ihre Items einen Hinweis zur Kenntnisnahme. Die Entscheidung „befördern“ ist vorbereitet, aber noch nicht angeschlossen (`STORY-042`), ebenso die Ursache „Projekt nicht erreichbar“ (`TASK-017`). `TASK-010` bis `TASK-012` warten auf Bestätigung; `STORY-041` bleibt „In progress“, weil die Erreichbarkeits-Ursache noch fehlt.

Am Ende kam `STORY-042` für das Backend (Release v0.7.2): Eine Note lässt sich über die API zu Task, Story oder Epic befördern, und ein offenes Item ohne Anhang lässt sich zur Note zurückstufen. Notizen und Specs wandern in beide Richtungen mit, die Herkunft steht als Link `origin` an beiden Seiten. Die Entscheidung „befördern“ eines Hinweises ist damit angeschlossen. Die Dialoge in der Oberfläche (`TASK-015`) fehlen noch, sie hängen an der Detailansicht von `TASK-019`. `TASK-013` und `TASK-014` warten auf Bestätigung; `STORY-042` bleibt „In progress“.

Zum Schluss `STORY-044` (Release v0.7.3): Ein Link oder Ereignis-Auslöser einer Note darf auf ein Item in einem anderen Projekt zeigen. Die API nennt das Ziel als „Projekt · Label“, ein unbekanntes Projekt wird mit `link_project_unknown` abgelehnt, und ein Merker in Projekt A wird fällig, wenn das Item in Projekt B den Zielstatus erreicht. Bisher feuerte ein Statuswechsel, den ein Sync in die Primärquelle einspielt, keinen Auslöser; das ist jetzt angeschlossen. Ist das Projekt eines Link-Ziels entfernt oder nicht lesbar, meldet die API den Link als `reachable: false` und legt einmal einen Hinweis „Projekt nicht erreichbar“ an, statt einen Fehler zu liefern. Damit ist die Ursache aus `STORY-041` geschlossen. Eine Oberfläche gibt es weiter nicht. `TASK-016`, `TASK-017` und `STORY-044` warten auf Bestätigung.

## Entscheidungen und Alternativen

| Entscheidung | Grund und Alternativen | Nachweis |
|---|---|---|
| Link-Ziel ist Projekt plus Item-Label | Markdown-Projekte haben keine `uid`; die interne `uid` wäre ein Bruch von `backend.md` §5. Retype zieht die Links nach. | STORY-037 |
| Gelöschte Notes bleiben wiederherstellbar | Gilt auch nach Projektwechsel; ein Wiederherstellen kann ein Duplikat ergeben. Alternative war endgültiges Löschen. | STORY-038 |
| Label-Nummern werden mit der Transaktion vergeben | Ein abgelehnter Schreibvorgang verbraucht keine Nummer. | 80e8b4a |
| `snoozed` ist gespeichert, „fällig“ nicht | `snoozed` wird wie `waiting` ausgewertet, damit die Oberfläche das Zurückstellen zeigen kann. Fälligkeit ist abgeleitet; ein gespeicherter Zustand würde einen Takt oder Schreibzugriffe beim Lesen brauchen. | STORY-040 |
| Hinweise nur bei Link-Rolle `reference` | Bei `trigger` meldet der Auslöser die Note schon fällig, ein zweiter Hinweis wäre doppelt; `origin` ist nur Herkunft. | STORY-041 |
| `decide(notice_id, …)` statt `decide(project, label, …)` | Die Hinweis-ID bestimmt Note und Seite; Wirkung zuerst, danach wird der Hinweis erledigt, damit ein Fehler ihn offen lässt. Abweichung von der Task-Spec. | TASK-010 |
| Umfang von 040/043 ohne HTTP-Routen | Routen und CRUD liegen in `STORY-039`; hier nur Domain, Service und Ports. | STORY-040, STORY-043 |
| Pfade unter `/projects/{project}` mit Projektname statt `source_id` | Notes und Topics sind nach Projekt plus Label adressiert (Regel §5); nur Index, Fällig-Abfragen und Optionen sind projektübergreifend. | STORY-039 |
| Topic-Filter braucht ein Projekt, schließt Unter-Topics ein | Labels zählen je Projekt, `TOPIC-001` gibt es also mehrfach. | STORY-039 |
| Kein Purge, kein „befördern“ über HTTP; `finish` nur `done`/`dropped` | Endgültiges Löschen bleibt dem Besitzer vorbehalten, Befördern gehört zu `STORY-042`. | STORY-039 |
| Rückstufung schließt das Item als Rejected | Der Besitzer hat Rejected bestätigt (Item wurde nicht umgesetzt); Alternative war Completed. Die Resolution nennt den Grund. | STORY-042, TASK-014 |
| Kein Rollback bei Abbruch zwischen Anlegen und Link `origin` | Item und Note liegen in getrennten Speichern. Der Link `origin` direkt nach dem Anlegen ist der Beleg für die Wiederholung; scheitert genau dieser Schritt, entsteht bei Wiederholung ein zweites Item bzw. eine zweite Note. Ein Rollback wurde nicht gebaut. | TASK-013, TASK-014 |
| Kein zweiter Hinweis für dasselbe unerreichbare Ziel, auch nicht nach einer Entscheidung | Die Spec sagt „wenn keiner offen ist“. Dann würde „behalten“ die Note beim nächsten Lesen sofort wieder fällig machen. Abweichung von der Task-Spec. Folge: Verschwindet ein Projekt ein zweites Mal, gibt es keinen neuen Hinweis. | TASK-017 |
| `link_infos` neben `links_of`, `due(check_links)` statt `due_all` | `links_of` bleibt unverändert (interne Aufrufer, Tests); die geprüfte Fassung heißt `link_infos`. `due_all` gibt es nicht, gemeint war die Fällig-Liste; der Zähler ruft `due` mit `check_links=False`, damit er billig bleibt. | TASK-017 |
| Umfang nur Backend | `TASK-015` (Dialoge) hängt an `TASK-019`, das noch offen ist; die Oberfläche folgt dort. | STORY-042 |
| Optionen werden bei jedem Aufruf gelesen | `NotesSettingsService` hält den Stand, die Services holen ihn bei jeder Nutzung; so wirken Änderungen ohne Neustart. Alternative wäre ein Neustart des Dienstes gewesen. | TASK-009 |
